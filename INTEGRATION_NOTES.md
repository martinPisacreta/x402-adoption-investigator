### Runner / integrator (`investigator/runner.py`, B4 + integrator)
1. Call `ctx.executor.cleanup()` in finalize AND in the error paths (`_error_envelope`). Without it the Zetaris
   objects (`X402_<RUN8>` database, `x402_<run8>` container) and the artifact server thread stay alive. The
   call is idempotent and never raises; `scripts/zetaris_cleanup.py` removes leftovers from crashed runs.
2. After `build_executor(...)`, set `mounts.zetaris_version = getattr(executor, "version", None)` (the executor
   logs in and runs `SHOW SERVER VERSION` at mount time, bounded to 10 s).
3. `build_executor(config, run_dir, log, run_id, zetaris_source=inp.options.get("zetaris_source"))`: the last
   argument is new and optional; the runner currently only passes the CLI override through `config`.
4. When `mode == "live"` and the returned executor is `SqliteExecutor`, `executor.fallback_reason` carries the
   real cause (`"zetaris_unreachable: Zetaris login failed: HTTP 401 ..."` or `"... unreachable: connection
   refused"`); the runner's recovery detail currently says "Zetaris not configured" in both cases.
5. `--require-zetaris` with an unreachable instance raises `E_ZETARIS_REQUIRED` from `build_executor` (stage
   `mounts`); later failures raise it from `ensure_views`/`execute` (stage `analyst`). Both carry
   `details.reason = "zetaris_required"`.

### Analyst (`investigator/agents/analyst.py`, B4)

### For the Verifier (B1 day 2): what the runner and the Analyst consume

`run_verifier(ctx, plan, observations) -> AgentResult` whose payload dict carries:
- `verifications: list[contracts.Verification]` (every sampled tx, incl. `unverifiable` + `reason: "fixture_miss"`);
- `conflicts: list[contracts.Conflict]` (`settlement_<field>` on a decode mismatch; the Analyst starts its own ids at
  `len(verifier_conflicts) + 1`, so number yours `k01..`);
- `chain_facts: list[dict]` shaped `{about: "wallet:base:0x...", predicate: "usdc_balance_atomic" | "tx_count" |
  "onchain_tx", value, url: "https://mainnet.base.org", checksum: "sha256:<hex>", at}` (B2's `keeper.chain_fact`
  accepts exactly this; the Analyst reads `usdc_balance_atomic` / `tx_count` from it);
- `observations: list[contracts.Observation]` for the RPC calls recorded through `collector.record_observation`
  (optional; they become evidence URLs and `output.sources[]` rows);
- and it writes `exports/settlements.json` (rows `tx_hash, payer, seller, amount_atomic, block_number, block_time,
  facilitator_from, status`).
The `base_rpc` family counts as available when a settlements export, chain facts or a decoded verification exists
(`analyst.chain_reached`), never from the deferred plan item. A complete reference that decodes the fixture Transfer
log, writes the export and the chain facts is `tests/test_agents_doubles.py::run_verifier` (a test double, not
production code; lift freely).

### Decisions worth knowing

- Pitfall gate semantics are the SPEC's OR-match (`policy_memories(fields, sources)`): mem-seed-007 carries
  `source:receipts`, so every receipts claim is revised with `basis_mismatch` + memory id in round 1. The registry keeps
  only the caveats SPEC 6.5 lists, so the loop is real work done by memory, not a staged omission.
- Metric ids are lowercase (`plan.schema.json` pattern): the deliberately wrong one is `unique_payers_summed`.
  `unique_payers_per_endpoint_max`, `top_hosts_by_listings`, `usdc_balance_atomic`, `tx_count` are reducer-only
  (`sql_backed=False`, `derivation.query_id = null`, confidence 0.7, `cross_checked: false`) because no committed query
  exposes them; a `q20` with MAX(payers_30d) over `catalog_resources` would let the first one be cross-checked (B3, optional).
- Reducers mirror B3's row semantics exactly: `host_of` imported from `zetaris.views_sqlite`, primary accept only,
  wallets lowercased; `catalog_hosts` therefore reports the java.net.URI-valid distinct hosts, matching the SQL side.
  README pitch numbers must come from the committed example outputs (B3's note 13 stands).
- The Analyst honours B3's contract: `ctx.executor.on_recovery = ctx.recover`, `ensure_views(exports, urls)`,
  `backend_label(result)` for `Derivation.backend`, `cleanup()` in finalize and error paths; the runner sets
  `mounts.zetaris_version` from `executor.version` and passes `zetaris_source` to `build_executor`.
- The Planner uses `registry.default_fetch_list` (B1) as the single source of truth for names/keys/mandatory flags;
  its own builder is only a fallback when the registry raises (no host).
- Generator calls are logged in a side file `logs/<run_id>/generator.jsonl` (prompt/response sha256, model, usage,
  transcript path; never headers or keys) because SPEC section 5 defines no `generator` run.jsonl event; transcripts go
  to `logs/<run_id>/transcripts/` and, with `--record-transcripts`, to `fixtures/transcripts/<example>/`.
- `output.plan` carries extra keys `metrics`, `hypotheses`, `hmem_memory_ids` (the schema allows them);
  `output.memory` carries `planned_feedback` only when H-MEM is not mounted.
- Rounds: a claim revised in round 1 (caveat or conflict fix applied by the Critic) is re-checked in round 2; anything
  still `revised` after the last round is rejected with reason "unresolved after N critic round(s)". With
  `max_critic_rounds: 1` every C3-revised claim would be rejected: the examples pin 2.
- `E_TIMEOUT` is raised (not `E_NO_SOURCES`) when the Collector failed because the deadline skipped every source.
