Why this needs agents

A script would pick one number. This system explains all of them.

Live, conflicting sources

Bazaar, the seller's receipts, Base RPC, x402-trust, Agent402 and vet402 each measure a different thing on a different window.

On-chain verification

Settlements are checked on Base by decoding the USDC Transfer log, never trusting tx.from, which is the facilitator.

Disagreement as output

When sources differ, the answer carries a Conflict object with each value, its measurement basis and why they differ.

Failure is normal

Sources go down mid-run. They become explicit "unavailable" entries with a logged recovery, never silent zeros.

What goes in, what comes out

A question in, a proof-carrying answer out

Input: one JSON question

{"run_id": "ex01-seller-audit",
 "input": {"question": "How real is the adoption of
   tienda.textokit.store? Who pays, how much,
   do they come back, and why do registries
   disagree about it?"}}

Output: one JSON envelope and a Markdown report

  • verdict chosen by rules, not by the model
  • claims[] each with evidence: URL + sha256, Base tx, or log line
  • conflicts[] with per-source values and the explanation
  • rejected_claims[] with the critique trail
  • unavailable[] instead of zeros

Architecture

Seven roles, bounded loops, every handoff logged

Planner→ Collector→ Keeper · World Model→ Verifier · Base RPC→ Analyst · Zetaris SQL→ Writer→ Critic

Computed twice

Every metric runs as committed SQL and as a pure Python reducer over the same exports. A claim survives only if both agree.

Critic rules C1 to C7

Evidence, recomputation, scope, staleness, conflict citation, memory caveats, plus a narrative pass that maps every number in the text to an accepted claim.

One event log

handoff, fetch, sql, claim, conflict, critique, retry and recovery lines in logs/<run_id>/run.jsonl.

The generator is used only by Planner, Writer and the Critic's second opinion; the rest is deterministic tooling5

Meterless, structural

World Model as shared state, H-MEM as policy

World Model

  • Entities: sellers, endpoints, payers, facilitators, settlements
  • Provenance on every row; facts without a URL, tx or log line are refused by the engine
  • Idempotent ingest, proved in every output: the second pass appends 0 events

H-MEM

  • Tiered memory store with a trust ledger and feedback per run
  • Pitfall memories ("never sum unique payers across endpoints", "receipts are self-reported") force caveats the Critic checks
  • Memory ablation committed: removing one memory changes fifteen citations, not the verdict
docs/METERLESS.md · conformance tests for both engines7
Zetaris, the federation layer

Every number is computed in Lightning SQL

  • Receipts, Bazaar catalog and registry snapshots registered as Zetaris sources through the local REST API
  • 19 committed analytics queries: sales by wallet class, repeat payers, concentration, registry counts, settlements vs receipts
  • The same ANSI SQL runs on SQLite offline; a test asserts both backends return equal rows
  • --require-zetaris turns any fallback into an error for the live demo

Logged per query

Executor, SQL sha256, row count, time used and tables with source URLs, in sql.jsonl and zetaris.jsonl. Live traces are committed separately from the offline examples.

Results on real data

Three questions, three proved answers

Seller audit

Verdict self_settled_mostly. 77 sales, 56 paid by the seller itself; 21 external sales by 4 payers, 0.044 USDC in total.

Catalog concentration

Verdict concentrated. 28,462 Bazaar resources, 2,680 hosts, 1,785 payTo wallets; the top host holds 29.5% of 824,796 calls in 30 days.

Payer dossier

Verdict adoption_thin. One external payer, one purchase of 0.001 USDC, the settlement verified on Base against the receipts.

The honest finding for our own store: most of its sales were self-tests. The system says so, with the proof.
